## Why this matters

Closures are not an advanced feature you reach for occasionally. They are how
every callback, every event handler, every module and every hook in React keeps
hold of the data it needs. If you have ever wondered why a `setTimeout` inside a
loop prints the wrong number, or why a React effect sees a stale value, the
answer is the same one both times.

Interviewers use closures because a shallow answer and a real one look very
different, and the difference shows up in one sentence.

## The idea

Every function carries a hidden reference to the scope it was **defined** in,
not the scope it is called from. When the outer function returns, its local
variables would normally be unreachable, but if an inner function survives, so
does the scope it points at.

The word that matters is **variable**, not value. A closure captures the binding
itself, so if that variable later changes, every closure over it sees the new
value.

## Captured, not copied

The reason `var` in a loop misbehaves is that a closure holds a variable rather
than a snapshot. Three callbacks over one `var i` all read the same box, and by
the time any of them runs, the loop has finished writing `3` into it.

Switching to `let` fixes it, and the reason matters more than the fix. The
specification creates a **new binding for each iteration** and copies the
previous value into it. So there are three variables, and each closure gets its
own.

## The interview angle

Asked "what is a closure", a weak answer stops at "a function that remembers its
variables". A strong answer adds the consequence:

> A closure is a function plus the scope it was defined in. It captures the
> variable, not the value, so closures over the same binding stay in sync, and
> the captured scope stays alive as long as the closure does.

That last clause is the one that leads somewhere, because it explains both the
loop puzzle and why closures can hold memory alive.

Expect these follow-ups:

- Rewrite the `var` loop two different ways.
- Implement `once`, `memoize`, `debounce` or a private counter.
- "How is this different from a private class field?"
- "How could a closure cause a memory leak?"

## Traps

- **Sharing a scope couples lifetimes.** A closure keeps its whole enclosing
  scope reachable, not only the variables it uses. A small handler defined
  beside a large array can keep that array alive.
- **Closures capture `this` differently.** An arrow function closes over the
  surrounding `this`; a regular function does not, and gets `this` from the call.
- **Loops are the classic trap, but not the only one.** Any variable reassigned
  after a closure is created shows the same behaviour, including in React where
  a stale value in an effect is exactly this bug.
- **`let` per iteration is a loop feature, not a block feature.** A single
  `let` outside the loop brings the shared-binding problem straight back.
