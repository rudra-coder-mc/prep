## Why this matters

Recursion is how you walk anything shaped like a tree, and a surprising amount
of what you handle every day is one. The DOM. A file system. A JSON response
with nested objects. A comment thread. A menu with sub-menus. Writing the loop
version of a tree walk by hand teaches you why the recursive version exists.

The other half of the topic is the reason it sits here rather than with the other
function topics. The call stack is the thing the event loop takes turns with, so
understanding what a call costs and when a frame goes away is the groundwork for
everything asynchronous that follows.

## What a frame holds

Every call pushes a frame onto the call stack. The frame holds the parameters
for that call, its local variables, and the position to return to when it
finishes. It is popped the moment the function returns, and not a moment before.

That last part is what makes recursion expensive. A function that calls itself
ten thousand deep has ten thousand frames alive at once, each with its own copy
of the locals, because none of them can return until the innermost one does. A
loop doing the same work has one frame that it reuses.

The stack has a fixed size. When there is no room to push another frame the
engine throws `RangeError: Maximum call stack size exceeded`. Roughly ten
thousand frames is the order of magnitude in a browser, but it depends on the
engine and on how large each frame is, so it is not a number to design against.

## Watching the stack

Nothing is computed on the way down. Each call defers to the next one and waits.
All the arithmetic happens on the way back up, as each frame receives the value
below it and returns.

Two things to take from this picture. The base case is what makes the stack
shrink, so a recursion without one grows until it crashes. And the work happening
on the way back up is why the depth cannot be traded away for free: those frames
are holding values that are still needed.

## When it runs out

There are two different ways to run out of stack, and they need different fixes.

**The base case is never reached.** Either it is missing, or the call does not
move towards it, or it is written after the recursive call so it is never
consulted. This is a bug, and the fix is in the function.

**The input is genuinely deep.** A linked list of a hundred thousand nodes, or
JSON nested a few thousand levels by something that generated it. The function
is correct and the data is bigger than the stack. The fix is to stop using the
stack, by rewriting the walk with an explicit one.

You may have read that proper tail calls solve this. They are in the
specification, and a call in tail position, where the result of the call is
returned directly with nothing left to do, is meant to reuse the current frame
instead of pushing a new one. In practice only JavaScriptCore, which is Safari,
implements it. V8 and SpiderMonkey do not and have said they will not. So write
tail calls if you like them, and never depend on them for depth.

## Turning recursion into a loop

Linear recursion, where each call makes one further call, becomes a loop with an
accumulator. Tree recursion, where each call makes several, becomes a loop with
an array standing in for the stack. The array is the same stack, moved from the
engine to the heap, which is why it can grow far past the frame limit.

Note the order. Popping from the end visits depth first, and the children come
out in reverse. Pushing them in reverse order, or taking from the front with a
queue, changes the traversal. Whichever you pick, say which one you picked,
because "it walks the tree" is not a specification.

## The interview angle

The questions are always the same handful: flatten a nested array, walk a tree,
deep clone an object, reverse a linked list, count the nodes in a JSON document.
A complete answer names four things:

> The base case, the recursive case, the step that makes progress towards the
> base case, and how deep the input can get. If the depth is unbounded or comes
> from outside, I would write it iteratively with an explicit stack.

The last clause is the one interviewers are listening for, because it is the
difference between someone who knows recursion and someone who has shipped it.

Expect these follow-ups:

- Rewrite it without recursion.
- What is the complexity, and where does the memory go?
- Naive `fib` is exponential. Why, and what fixes it?
- What happens if the object has a cycle?

## Traps

- **Depth and repeated work are different problems.** Naive `fib(35)` is slow
  because it recomputes the same subtrees, not because the stack is deep. That
  one is fixed by memoising, and no rewrite to a loop will help it.
- **The base case has to come first.** Written after the recursive call, it is
  unreachable and the function never terminates.
- **Cycles never terminate.** A deep clone or a tree walk over data that
  references itself recurses forever. Keep a `WeakSet` of what you have seen.
- **Untrusted depth is a crash.** Recursing over JSON that came from a request
  means the caller chooses your stack depth.
- **Catching the overflow does not fix it.** `RangeError` is catchable, and the
  handler runs on a stack that has just been unwound to nothing useful. It is a
  way to observe the limit, not a way to survive it.
- **Every frame keeps its locals alive.** A recursive function holding a large
  array in a local keeps one per level, so depth multiplies memory as well.
