## Why this matters

`0.1 + 0.2` is `0.30000000000000004`, and every developer has seen that. Far
fewer can say what to do about it, which is the part an interview asks and the
part a billing bug turns on.

The whole topic comes out of one decision: JavaScript has a single number type,
and it is a binary floating point number. Everything surprising below follows
from that, including the ones that look unrelated, like an id from the database
arriving as the wrong id.

## One number type, and it is a float

A `number` is a 64-bit IEEE 754 double. There is no integer type. `5` and `5.0`
are the same value, and `Number.isInteger(5.0)` is `true` because the value has
no fractional part, not because it was written without one.

Those 64 bits are one sign bit, eleven for the exponent and fifty-two for the
significand. That buys about fifteen to seventeen significant decimal digits, and
it buys them in binary. A fraction is exact only when its denominator is a power
of two: `0.5`, `0.25` and `0.125` are exact, and `0.1`, `0.2` and `0.3` are not,
the same way a third is not exact in decimal.

So `0.1` is not stored as a tenth. It is stored as the nearest double to a tenth,
and every arithmetic result is rounded to the nearest double again.

The error is tiny and it accumulates. Adding `0.1` ten times gives
`0.9999999999999999`, and `(0.1 + 0.7) * 10` is `7.999999999999999`, so
`Math.floor` on it returns `7`. That last one is how a rounding bug reaches
production: the value is right to fifteen digits and the floor is off by one.

## Comparing floats

Never compare computed floats with `===`. Compare the size of the difference
against a tolerance:

```js
Math.abs(0.1 + 0.2 - 0.3) < Number.EPSILON // true
```

`Number.EPSILON` is `2.220446049250313e-16`, the gap between `1` and the next
double above it. That makes it the right tolerance near `1` and the wrong one
everywhere else, because the gap between doubles grows with the magnitude of the
number. Around `1e10` consecutive doubles are about `1e-6` apart, so two results
that differ only by rounding error are further apart than `Number.EPSILON` and a
fixed tolerance calls them different.

> A tolerance is a decision about your data, not a constant you import. Compare
> relative error, `Math.abs(a - b) <= Number.EPSILON * Math.max(Math.abs(a), Math.abs(b))`,
> or pick an absolute tolerance you can defend, such as half a penny.

## Rounding, and what `toFixed` does

`toFixed` returns a **string**, and it rounds the double that is actually stored
rather than the decimal you wrote:

```js
;(1.005).toFixed(2) // '1.00', because 1.005 is stored as 1.00499999999999989…
;(2.675).toFixed(2) // '2.67', for the same reason
;(1e21).toFixed(2) // '1e+21', exponential notation above 1e21
```

Neither of those is a bug in `toFixed`. The literal `1.005` was already below a
thousandth-and-a-half before `toFixed` saw it, so rounding half up rounds down.

`Math.round` has its own edge: it rounds half **towards positive infinity**, not
away from zero. `Math.round(1.5)` is `2` and `Math.round(-1.5)` is `-1`, not
`-2`. `Math.round(-0.5)` is `-0`, which is falsy, prints as `-0`, and is `===` to
`0`.

## Where the integers run out

Integers are exact up to `Number.MAX_SAFE_INTEGER`, which is `2**53 - 1`, or
`9007199254740991`. Past it, doubles are spaced more than one apart and integers
start sharing a representation:

```js
Number.MAX_SAFE_INTEGER + 1 === Number.MAX_SAFE_INTEGER + 2 // true
9007199254740993 // 9007199254740992
```

The second line is the dangerous one. Nothing threw, nothing warned, and a
literal turned into a different number on its way into the program. A 64-bit id
from a database, a Twitter-style snowflake id, or a nanosecond timestamp all live
past that boundary, and `JSON.parse` will silently round every one of them.

`bigint` is the fix for whole numbers of any size. It is a separate type, with a
separate literal:

```js
9007199254740993n + 2n // 9007199254740995n
1n + 1 // TypeError: Cannot mix BigInt and other types
5n / 2n // 2n, division truncates
Math.sqrt(4n) // TypeError: Cannot convert a BigInt value to a number
JSON.stringify({ id: 1n }) // TypeError: Do not know how to serialize a BigInt
```

That refusal to mix is deliberate. Every other pair of types in JavaScript gets
converted and guesses; this is the one place the language would rather throw than
lose precision quietly. `1n == 1` is still `true`, because `==` converts and
`===` does not.

## Money

Money is not a floating point problem, it is a floating point trap: the values
look small and well behaved, and the errors are invisible until a total is
reconciled. Two answers, and both are fine:

- **Integer minor units.** Store pennies, not pounds. Every amount is an integer,
  every addition is exact, and you divide by 100 exactly once, at the edge, to
  display. This is what most systems do and it is the cheaper answer.
- **A decimal library.** `decimal.js` or `big.js` if you need division, tax
  splits, or more than two decimal places of real precision.

Then format with `Intl.NumberFormat` rather than by hand:
`new Intl.NumberFormat('en-GB', { style: 'currency', currency: 'GBP' }).format(1234.5)`
gives `'£1,234.50'`, with the grouping and the symbol placement right for the
locale.

`bigint` works for money too, and it is integer minor units with a bigger
ceiling. It costs you JSON serialisation and every function in `Math`, so reach
for it when the amounts genuinely exceed a safe integer rather than by default.

## The interview angle

> **"Why is `0.1 + 0.2` not `0.3`?"**
> Because `number` is a binary double, and a tenth is not representable in binary
> any more than a third is in decimal. Both operands are stored as the nearest
> double, and the sum is rounded again. Say the fix in the same breath: compare
> with a tolerance, and hold money as integer minor units.

> **"When is floating point fine?"**
> When the value is a measurement rather than a count of something exact:
> positions, durations, weights, scores, anything already approximate before it
> reached you. It is not fine for money, for ids, or for anything where two
> values have to compare equal after being computed by different routes.

## Traps

- **`toFixed` returns a string.** `(1.5).toFixed(2) + 1` is `'1.501'`. Convert
  back, or format only at the last moment.
- **`Math.round` is not "round half away from zero".** It rounds half up towards
  positive infinity, so negative halves round the way most people do not expect.
- **`JSON.parse` rounds large integers silently.** An id past
  `MAX_SAFE_INTEGER` arrives wrong with no error. Ask the API for it as a string.
- **`Number.EPSILON` is a tolerance for values near 1.** It is too small to be
  meaningful for large numbers and unnecessarily large for tiny ones.
- **`0.1 + 0.2` is only the famous one.** Any chain of decimal arithmetic drifts.
  A total that is compared against an expected total needs a tolerance or
  integers, not luck.
- **`parseFloat` and `Number` do not add precision.** They produce the same
  doubles as a literal would.
